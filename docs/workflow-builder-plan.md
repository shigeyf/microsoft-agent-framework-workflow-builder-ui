# YAML ワークフロー GUI 開発計画と実装状況

## 1. 目的

Microsoft Agent Framework の宣言型ワークフロー仕様をもとに、YAML を手入力ではなくキャンバスとフォームで組み立てられる React アプリを開発する。

目的は以下の 3 点。

- YAML 仕様の習得を支援する
- ワークフロー定義のミスを減らす
- 生成された YAML をそのまま保存・コピーできる体験を提供する

## 2. 対象ユーザー

- AI エージェントや自動化フローを設計する開発者
- YAML レイアウトを理解し始めたプロトタイプ担当者
- 宣言型ワークフローの設計レビューを行うチーム

## 3. 実装済みの機能

### 3.1 ワークフローの編集

- ワークフロー名 / 説明 / トリガー種別 / 入力パラメータの編集
- キャンバス上でのアクション追加・削除・編集・移動
- `If` と `ConditionGroup` をコンテナとして描画し、内部に分岐を保持
- コンテナの折りたたみと展開
- アクションの追加・削除のたびに自動整列し、カードが重ならない。ドラッグ後は `Auto arrange` で整列し直せる
- 分岐末尾の `+` からの追加、結線上の `+` からの挿入

| `InvokeMcpTool`        | ○      | ○   |
| `HttpRequestAction`    | ○      | ○   |

対応可否の根拠は `declarative-workflow-spec-ja.md` の 6.9 節を参照。

※ `Foreach` は両言語に存在するがプロパティ名が異なるため、選択中の Style に応じて `items` / `value` / `index`（C#）と `source` / `itemName` / `indexName`（Python）を使い分ける。入力欄のラベルも Style で切り替わる。

### 3.3 未対応のアクション

下記は専用の編集フォームを持たない。いずれも Python / C# の両方で使える。

| kind | 対応に必要なもの |
| --- | --- |
| `EndConversation` | プロパティなし。カード表示のみで足りる |
| `SetMultipleVariables` | `assignments` 配列の編集 UI |
| `ParseValue` | `variable` / `value` / `valueType` |
| `SetTextVariable` / `ResetVariable` / `ClearAllVariables` | 単一の変数指定 |
| `EditTable` / `EditTableV2` | テーブル操作の UI |
| 会話操作系 | C# 専用。スタイル別フィルタとの連携が必要 |

これらを含む YAML を読み込んでも、未解釈のプロパティは `extra` に保持され、再出力で失われない。実際のスキーマは `declarative-workflow-spec-ja.md` の 6.10 節に記載している。

### 3.4 YAML の入出力

- 入力内容から C# 形式 / Python 形式の YAML をリアルタイム生成
- クリップボードへのコピー
- ローカルファイルの読み込み
- 公式サンプル 12 件を URL から取得して描画

### 3.5 スタイルの扱い

2 つの形式は相互変換できないため、アクションまたは入力が 1 つでもある間は Style を変更できない。作り直すための `New workflow` ボタンを用意している。

アクション一覧は選択中の Style で使えるものだけに絞り込む。

## 4. アーキテクチャ

```text
src/ui/src/features/workflow-builder/
├── WorkflowBuilder.tsx     状態の保持と各操作のオーケストレーション
├── types.ts                ドメインモデルの型定義
├── data.ts                 アクションの初期値
├── samples.ts              公式サンプルの URL 一覧と取得
├── domain/                 座標に依存しない純粋なモデル操作
│   ├── actionTree.ts       then / else / conditions を跨ぐ探索・挿入・削除
│   ├── branches.ts         分岐の正準的な順序
│   ├── nodeIds.ts          キャンバス上のノード ID 規約
│   └── styles.ts           言語別の対応アクションとスタイル固定の判定
├── graph/                  モデル → 描画用ビューモデル
│   ├── layout.ts           座標定数
│   ├── buildNodes.ts       ノード生成と寸法計算
│   ├── buildEdges.ts       結線生成
│   ├── autoLayout.ts       座標を持たない読み込みデータの自動配置
│   └── useWorkflowGraph.ts 上記をまとめるフック
├── components/             React コンポーネント
└── utils/
    ├── yaml.ts             モデル → YAML
    └── parseYaml.ts        YAML → モデル
```

依存の向きは `domain` → `graph` → `components` の一方向とする。`domain` と `graph` は React に依存しない純粋な関数で構成し、単体テストの対象とする。

## 5. 実装上の重要な決定

### 5.1 分岐を平坦化しない

`If` と `ConditionGroup` は親の `actions` 配列に属する 1 つのアクションであり、その中身は `then` / `else` / `conditions[].actions` という別の配列である。この 2 層構造をキャンバス上でも保つ。詳細は `declarative-workflow-spec-ja.md` の 11 節を参照。

### 5.2 未知のプロパティを保持する

パーサーが解釈しなかったキーは `ActionModel.extra` に退避し、書き出し時にそのまま再出力する。仕様には存在するが UI が未対応のプロパティ（`body` や `connection.name` など）や、未対応の kind を読み込んでも内容が失われない。

### 5.3 コンテナの寸法は構造から求める

ネストした分岐が重ならないよう、行の高さと幅を座標ではなく木の構造から算出する。

- `subtreeHeight(action)` — 行の高さ
- `subtreeWidth(action)` — 分岐末尾の `+` の位置、挿入位置、自動配置で共通利用

固定値（`node.width` など）で代用すると、ネストしたコンテナの内側に `+` が入り込む。

### 5.4 コールバックは `node.data` 経由で渡す

キャンバスとビルダー間の通知に `window` のカスタムイベントを使わず、React Flow の `node.data` / `edge.data` に型付きコールバックを載せる。

## 6. テスト方針

`npm test` で Vitest を実行する。重視しているのは次の 3 種類。

1. **往復テスト** — `parse → buildYaml → parse` でモデルが一致すること
2. **プロパティ網羅テスト** — 元 YAML と再出力 YAML のプロパティパスを比較し、欠落を検出する。往復テストは読み書き双方が無視するフィールドを検出できないため、その死角を埋める
3. **レイアウト不変条件** — カード同士が重ならないこと、コンテナ枠が自分の部分木だけを覆うこと、分岐末尾の `+` がネストしたコンテナの内側に入らないこと

テストデータには公式サンプル 11 件をそのまま fixture として使用する。C# の単体テスト由来の `loop_each` / `loop_break` を含む。

## 7. 残課題

- `SetMultipleVariables` / `ParseValue` / `EndConversation` などの専用フォーム。現状は `extra` で内容を保持するのみ
- C# 専用アクション（会話操作など）の対応
- `GraphCanvas.tsx` の分割

### 7.1 実用化に必要な追加 TODO

以下は「ワークフローを作る UI として実運用レベルで必要になる」事項の候補である。優先度は次の通りとする。

- P1: 早期に実装すべき必須機能。開発者が実際に設計・検証・修正を進めるうえで重要
- P2: 実用性を大きく向上させるが、P1 を先に固めてから着手してよい機能
- P3: 将来の成熟化・運用改善に有効だが、初期の価値提供には優先度を下げてもよい機能

#### P1: 必須

- [ ] 変数スコープとライフサイクルの管理
  - アクションが参照・更新できる変数をスコープ別に表示する
  - ループ変数、条件分岐内変数、グローバル変数の区別を視覚化する
  - `SetVariable` / `SetValue` / `ParseValue` の変数名候補を自動補完する
  - 未定義変数の参照、重複定義、異なる型の再代入を検知する

- [ ] アクションへ渡す入力値の型と値の補助
  - `parameter` / `body` / `arguments` などの入力項目をスキーマベースで提示する
  - 文字列、数値、ブール、配列、オブジェクトで入力フォームを切り替える
  - `enum` / `oneOf` / `required` を UI に反映し、必須項目を強調する
  - 例: `InvokeFunctionTool` と `HttpRequestAction` の JSON ボディの入力支援

- [ ] 評価式の入力補助と検証
  - `if` 条件、比較式、マッピング式の入力時に変数名と関数名を補完する
  - `contains`, `startsWith`, `length`, `toLower`, `jsonPath` などの利用可能関数を一覧表示する
  - 式の構文エラーのハイライトと、エラー理由の説明を出す
  - 変数参照の型が不一致している場合に警告する

- [ ] 実行時データのプレビューとデバッグ支援
  - 入力サンプル JSON を与えて、各アクションの出力がどう変わるかをプレビューする
  - `If` の真偽判定、配列のマッピング結果、HTTP 応答の内容をステップ単位で確認できるようにする
  - 「このノードが実行される条件」を説明するデバッグ表示を追加する

- [ ] ワークフロー検証と『危険な設定』の警告
  - 参照だけの変数、未使用の変数、到達不能ノード、循環参照を検出する
  - `goto` / `end` / `break` の制御フローが破綻していないかをチェックする
  - ループ内で破壊的変更が起こる設定や、巨大な外部 API 呼び出しを警告する
  - YAML 生成前にフォーム上で軽いバリデーションを実行する

#### P2: 価値拡大

- [ ] 再利用可能なテンプレートとサブフロー化
  - 一般的なパターン（質問 → 変数保存 → 条件分岐 → 関数呼び出し）をテンプレート化する
  - タスク単位のサブワークフロー化と、参照型の再利用をサポートする
  - 共有可能な action library と、社内標準テンプレートの保存を可能にする

- [ ] 外部ツールや API スキーマの自動取り込み
  - OpenAPI / MCP / 関数定義から入力パラメータを自動抽出し、フォームに反映する
  - `InvokeFunctionTool` のツール名と引数を自動補完する
  - 返却スキーマから「どのフィールドを後続アクションで使えるか」を可視化する

- [ ] 入力フォームの階層化と条件付き表示
  - フィールドの依存関係（例: `method` が `GET` のときに `query` を表示、`POST` のときに `body` を表示）を制御する
  - `advanced mode` / `simple mode` の切り替えを追加する
  - 不要なプロパティを非表示にして、初心者向けと上級者向けの UI を切り分ける

- [ ] 批量編集と検索・ナビゲーション
  - ノードやプロパティ名を検索してすぐ開ける機能を追加する
  - 同種アクションをまとめて編集できるようにする
  - アクションの一覧と依存関係を表示し、全体マップから目的の箇所へジャンプできるようにする

- [ ] 変更差分と履歴管理
  - YAML 変更差分を可視化し、どこで何が変わったかをレビューできるようにする
  - Undo / Redo の粒度を詳細化し、ノード単位に戻せるようにする
  - 主要な構成変更にコメントや説明を残せるようにする

- [ ] セキュリティと運用面の制御
  - `secret`, `token`, `password` のような機密項目のマスキングと扱いを明確化する
  - 環境変数や構成値の束縛先を管理できるようにする
  - 生成 YAML の破壊的変更を防ぐための review / approval フローを考慮する

- [ ] 既存の YAML との相互運用テスト
  - 実運用 YAML を大量に読み込み、UI で再編集してもプロパティが維持されることを確認する
  - 公式サンプル以外の実ファイルに対する変換差分テストを増やす
  - 非対応アクションや拡張プロパティを適切に扱うための回帰テストを追加する

#### P3: 発展期

- [ ] 協業とドキュメント化
  - アクションごとに説明文、使い方、警告、例を表示する
  - ワークフロー全体のコメントやメモを残せるようにする
  - 他メンバーがレビューしやすいよう、ステップ単位の説明と依存関係の注記を残せる UI を用意する

- [ ] アクセシビリティと操作者体験の改善
  - キーボード操作、ショートカット、フォーカス遷移を整える
  - 画面サイズが小さいときのレイアウト崩れを解消する
  - エラー時に次にやるべき修正が一目で分かるようにする

- [ ] 進捗可視化と運用データの収集
  - ワークフローの実行サマリー、例外率、再試行回数を UI 上で確認できるようにする
  - 通常のフローと例外系の分岐が見分けやすいように、ビジュアルの強調を行う
  - 改善候補の提案（未使用ノード、複雑化している分岐、評価式の重複）を示す

- [ ] 保存状態と自動復元
  - 編集途中のワークフローがブラウザ再読込時にも保持されるようにする
  - 重要な変更前に snapshot を残し、比較や復元を可能にする

- [ ] コピー/ペーストと再利用支援
  - ノードやサブツリーの複製と再利用を容易にする
  - よく使う構成の quick action とテンプレート保存をサポートする

上記の分類は、現在の「編集可能なグラフ UI」から一段進んで、実際にチームで設計・レビュー・運用するワークフロー作成ツールとして必要になる機能群を、実装優先度に沿って整理したものである。

## 8. 受け入れ基準

- 公式サンプルを読み込み、YAML と一致するグラフを描画できる
- 読み込んだ YAML を再出力してもプロパティが失われない
- C# と Python の差異を UI が区別する
- `npm run build` / `npm test` / `npm run lint` がすべて成功する
